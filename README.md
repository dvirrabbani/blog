# Notes — a personal blog

Next.js (App Router) + Prisma + SQLite, with a password-protected admin panel for writing posts.

## Setup

```bash
npm install
```

Configure `.env` (already created for local dev):

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | SQLite file path |
| `SESSION_SECRET` | Signs the session cookie — regenerate for production |
| `ADMIN_EMAIL` / `ADMIN_PASSWORD` / `ADMIN_NAME` | The admin account created by the seed script |

Create the database and seed the admin account plus sample posts:

```bash
npm run db:migrate
```

```bash
npm run db:seed
```

Then start the dev server:

```bash
npm run dev
```

- Blog: http://localhost:3000
- Admin: http://localhost:3000/admin (sign in with `ADMIN_EMAIL` / `ADMIN_PASSWORD`)

## Changing the admin password

Edit `ADMIN_PASSWORD` in `.env`, then re-run `npm run db:seed` — the seed upserts, so it updates the existing account without touching your posts.

## How it works

- **Posts** live in SQLite via Prisma (`prisma/schema.prisma`). Each has a unique slug, an excerpt, and a published flag — unpublished posts are drafts and never appear on the public site.
- **Auth** is a signed JWT in an httpOnly cookie (`src/lib/session.ts`). `requireUser()` in `src/lib/dal.ts` guards the admin layout and every mutating server action.
- **Post content** is markdown, written in the editor at `src/app/admin/posts/markdown-editor.tsx` — a toolbar plus a live preview that renders with the same component as the public post page, so what you see is what publishes.

  Supported: `**bold**`, `*italic*`, `` `code` ``, `[links](url)`, `![images](url)`, `##`/`###` headings, `-` and `1.` lists, `>` quotes, ``` fenced code blocks, and `---` rules. Parsed into React elements (never `dangerouslySetInnerHTML`) by `src/components/post-content.tsx`, which also restricts link and image URLs to http/https/mailto/relative so a `javascript:` URL can't execute.

  Toolbar buttons toggle: pressing **B** on already-bold text unwraps it. `Ctrl/Cmd+B`, `+I`, and `+K` are bound to bold, italic, and link.
- **Images** are cropped in the browser before upload (`src/components/image-upload-dialog.tsx`), so only the cropped region is ever sent. Ratio presets are Free, 16:9, 4:3, 3:2 and 1:1; output is capped at 2000px wide and re-encoded as JPEG.

  Two entry points, both using the same dialog: the **Cover image** field on the post form (defaults to 16:9, shown on the home page, the post header, and as the OpenGraph image), and the **Image** button in the editor toolbar (defaults to Free, inserts `![alt](url)` at the cursor).

  The seeded post **Writing with pictures** demonstrates both. Its two images are generated by `prisma/example-images.ts` on each seed rather than committed, since `public/uploads/` is gitignored — delete the post and they become orphans like any other unused upload.
- **Seeded posts** are defined in `prisma/seed-posts.ts` (title, excerpt, cover, publish date) with each body in `prisma/content/<slug>.md`. Three of them document the project itself: *Building this blog*, *Running this blog locally*, and *What comes next*. Edit the markdown and re-seed to change them — the seed upserts by slug and never overwrites an existing post, so edits made in the admin panel are safe.

  Uploads go to `POST /api/upload` (`src/app/api/upload/route.ts`), which requires a signed-in admin, caps size at 8MB, and identifies the file by its magic bytes rather than trusting the client's `Content-Type` or filename — a script renamed to `.jpg` is rejected. Filenames are server-generated UUIDs, so nothing from the client reaches the filesystem path. Files land in `public/uploads/`, which is gitignored.
- **Site name and description** are in `src/lib/site.ts`.

## Known limitations

- Deleting a post does not delete the images it used — orphaned files stay in `public/uploads/`.
- Cropping is destructive: the original upload is never stored, so re-cropping means re-uploading.

## Deploying

See **[DEPLOYMENT.md](DEPLOYMENT.md)** for the full walkthrough. In short: the app runs on Vercel as-is, with Turso replacing the local SQLite file and Vercel Blob replacing `public/uploads/`. The schema, migrations, and query code are identical in both environments — Turso speaks the same libSQL protocol through the same adapter — and `saveUpload()` picks its backend at runtime based on whether `BLOB_READ_WRITE_TOKEN` is set.

On a host with a persistent writable disk, both managed services are optional: mount a volume at `public/uploads/`, keep the SQLite file on it, and leave the blob token unset.

Environment variables in production:

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | `libsql://…` URL of the hosted database |
| `DATABASE_AUTH_TOKEN` | Token for that database (omit for a local file) |
| `SESSION_SECRET` | Signs session cookies — the app refuses to boot in production without it |
| `BLOB_READ_WRITE_TOKEN` | Enables blob storage; unset means write to local disk |
